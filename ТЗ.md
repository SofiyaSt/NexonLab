# Техническое задание
## Nexon Registry — единая электронная регистратура

**Статус документа:** рабочий черновик  
**Версия:** 0.1

Пользовательские сценарии описаны в документах [Поток пациента](Пользовательский%20поток.md) и [Поток врача](Поток%20врача.md).

Для первой итерации веб-макета интеграция с ЭДО ограничена итоговым заключением врача: Registry завершает запись после получения статуса подписания `signed` и `documentId` для связанного `appointmentId`.

## 1. Общая информация и цели

### 1.1. Наименование системы

Nexon Registry — информационная система для поиска медицинских специалистов и клиник, управления расписанием и записи пациентов на приём.

### 1.2. Назначение системы

Система предоставляет единый цифровой интерфейс для пациентов и медицинских работников. Она объединяет данные собственной регистратуры и подключённых сервисов Nexon Labs и предоставляет клиентским приложениям согласованный API (Backend-for-Frontend, BFF).

Система включает следующие пользовательские интерфейсы:

- интерфейс пациента для поиска врача, просмотра доступного времени и управления своими записями;
- интерфейс медицинского работника для просмотра расписания и записей;
- административный интерфейс для управления справочниками, расписаниями, квотами и настройками (состав и права администраторов уточняются при проектировании).

### 1.3. Цели создания

Система должна:

1. Обеспечить единый каталог клиник, врачей и специальностей.
2. Позволить пациенту находить доступные приёмы, записываться, отменять и переносить запись.
3. Предоставить врачу актуальное расписание и список записанных пациентов в пределах его полномочий.
4. Исключать конфликтующие записи при одновременных запросах.
5. Поддерживать разные типы оплаты и квотирования: ОМС, ДМС и платный приём.
6. Создать основу для интеграции с CityOS Identity, ЭДО, Vitals и другими сервисами экосистемы.
7. Обеспечить защиту персональных данных, аудит действий и наблюдаемость работы системы.

### 1.4. Пользователи и внешние системы

Основные категории пользователей:

- **Пациент** — ищет специалиста и управляет собственными записями.
- **Врач** — просматривает своё расписание и сведения, необходимые для оказания медицинской услуги.
- **Оператор или администратор клиники** — управляет расписаниями, слотами, квотами и справочными данными согласно назначенной роли.
- **Системный администратор** — настраивает систему и доступы, не получая доступ к медицинским сведениям без отдельного основания.

Предполагаемые внешние системы:

- CityOS Identity / Keycloak — аутентификация и единый вход;
- ЭДО — подписание согласий и обмен документами;
- Vitals — получение показателей пациента при наличии разрешения;
- сервисы доставки уведомлений — электронная почта.

### 1.5. Границы системы

Nexon Registry отвечает за каталог регистратуры, расписания, бронирование и управление записями, согласия в рамках определённого объёма интеграции, а также передачу запросов внешним сервисам. Система не заменяет медицинскую информационную систему, не ставит диагнозы и не принимает клинические решения.

Внешние сервисы являются владельцами своих данных и процессов. Система должна обрабатывать недоступность интеграций так, чтобы сбой необязательного внешнего сервиса не приводил к потере или некорректному созданию записи.

### 1.6. Термины

- **Слот** — интервал времени, доступный для записи к конкретному врачу или специалисту.
- **Запись на приём** — подтверждённое резервирование слота пациентом.
- **Квота** — ограничение числа или доли слотов, доступных для заданного типа оплаты.
- **Буфер** — интервал до или после приёма, в течение которого слот нельзя назначить на другую запись.
- **Лист ожидания** — очередь пациентов, желающих занять освободившееся время.
- **Идемпотентность** — свойство повторного запроса с тем же ключом не создавать дублирующую операцию.
- **Персональные данные (ПДн)** — сведения, относящиеся к прямо или косвенно определённому физическому лицу.

## 2. Технические требования

### 2.1. Архитектура

1. Система должна предоставлять серверное API для клиентских приложений пациента, врача и администрирования.
2. Серверная часть должна быть модульной и поддерживать разделение доменных областей: каталог, расписание, бронирование, пользователи и доступы, уведомления, аудит и интеграции.
3. Внешние сервисы должны подключаться через изолированные адаптеры. Для каждой интеграции должен быть определён контракт с указанием версии API внешней системы, форматов запросов и ответов, ошибок и правил совместимости.
4. Отказ внешней интеграции должен локализоваться: недоступность сервиса маршрутов, Vitals или ЭДО не должна нарушать операции записи, не зависящие от этой интеграции.
5. Для длительных фоновых операций и доставки уведомлений должна использоваться очередь задач.
6. API Nexon Registry для клиентских приложений должно быть версионируемым; версия указывается в пути API (например, `/api/v1/`). Изменения контракта не должны без необходимости нарушать работу уже подключённых клиентов.

### 2.2. Технологический стек

Целевой стек проекта:

- серверная часть: Node.js 22, TypeScript, MoleculerJS;
- клиентские приложения: React, Vite, TypeScript;
- основное хранилище: PostgreSQL;
- кэширование и фоновые очереди: Redis и BullMQ;
- синхронный API в текущем объёме: REST, в том числе для чтения каталога и расписания, а также для создания, отмены и переноса записей;
- GraphQL может быть добавлен как расширение для гибких запросов чтения каталога и расписания, если этого потребуют клиентские приложения. Внедрение GraphQL не является обязательным требованием текущего объёма и не заменяет предусмотренные REST-операции изменения данных.

Допускается уточнение конкретных версий компонентов при реализации при условии совместимости с целевой средой развёртывания и поддержки безопасности.

### 2.3. Данные и целостность

1. PostgreSQL является источником истины для локальных записей, расписаний, квот и аудита.
2. Моменты времени записей должны храниться как абсолютные моменты времени и передаваться API в UTC в формате ISO 8601 с суффиксом `Z`. Клиентские приложения преобразуют время в локальное для отображения. Для расписаний, задаваемых по местному времени клиники, должна храниться её часовая зона в формате IANA (например, `Europe/Moscow`).
3. Для записей должны храниться идентификаторы пациента, врача, филиала, услуги, временной интервал, тип оплаты, статус и временные отметки создания и изменения.
4. Структура данных должна позволять хранить несколько филиалов и локальные часовые пояса.
5. Ограничения целостности должны обеспечиваться на уровне приложения и базы данных там, где это возможно.
6. Операции бронирования, отмены и переноса должны выполняться атомарно. При конкурентном изменении расписания необходимо применять транзакции и блокировки либо эквивалентные механизмы сериализации.
7. Слоты, записи и квоты не должны переводиться в противоречивое состояние при повторной доставке события или повторе запроса.

### 2.4. API и обработка запросов

1. Все входные данные должны проходить проверку схемы и бизнес-ограничений до выполнения операции (см. [пояснение о валидации запросов](Валидация%20запросов.md)).
2. Изменяющие запросы на создание, перенос и отмену записи должны поддерживать ключ идемпотентности (`Idempotency-Key`). Порядок его использования и обработки описан в [пояснении об идемпотентности](Идемпотентность.md).
3. Для API должны быть определены форматы ошибок, пагинация, фильтрация и сортировка списков (см. [пояснение о контракте API и формате ответов](Контракт%20API%20и%20формат%20ответов.md)).
4. Доступ к объектам должен проверяться по роли и принадлежности: пациент может управлять только своими записями, врач — только данными в пределах назначенных ему клиник и расписаний (см. [пояснение о проверке доступа](Проверка%20доступа%20к%20данным.md)).
5. Публичные операции поиска и записи должны иметь ограничения частоты запросов (см. [пояснение об ограничении частоты запросов](Ограничение%20частоты%20запросов.md)).
6. Секреты, пароли, ключи интеграций и строки подключения не должны храниться в исходном коде или открытых конфигурационных файлах (см. [пояснение об управлении секретами](Управление%20секретами.md)).

### 2.5. Интеграции

1. Интеграции должны иметь явные тайм-ауты, ограниченное число повторов и защиту от длительной недоступности внешней системы (например, circuit breaker; см. пояснения о [тайм-аутах и повторах](Тайм-ауты%20и%20повторы%20интеграций.md) и [circuit breaker](Circuit%20breaker.md)).
2. Повторная отправка запроса внешнему сервису должна учитывать идемпотентность и не создавать дублирующих документов или уведомлений (см. [пояснение об идемпотентности](Идемпотентность.md)).
3. Ошибка интеграции должна фиксироваться с техническим идентификатором и статусом обработки без записи избыточных ПДн в журналы (см. [пояснение о журналировании ошибок интеграций](Журналирование%20ошибок%20интеграций.md)).
4. Для каждой интеграции должны быть определены владелец данных, формат и версия контракта, правила авторизации, обработка ошибок и допустимая деградация (см. [пояснение о контракте внешней интеграции](Контракт%20внешней%20интеграции.md)).
5. Недоступность сервиса маршрутов должна отключать только построение маршрута; запись на приём должна оставаться доступной (см. [пояснение о circuit breaker](Circuit%20breaker.md)).

### 2.6. Развёртывание и эксплуатация

1. Для локальной разработки должна быть предусмотрена конфигурация запуска сервисов в контейнерах одной командой.
2. Конфигурация должна разделять локальную, тестовую и производственную среды.
3. Система должна поддерживать контейнерное развёртывание и целевой вариант запуска в Docker Swarm.
4. Остановка приложения должна завершать обработку активных операций и корректно закрывать соединения с БД, очередью и внешними сервисами.
5. Должны поддерживаться резервное копирование базы данных и проверяемое восстановление.
6. Схема и изменения базы данных должны поставляться в виде версионируемых миграций.

### 2.7. Наблюдаемость

1. Система должна предоставлять структурированные журналы, метрики и распределённые трассировки.
2. Минимальные метрики: количество запросов, доля ошибок, задержка API (включая p95), занятость очередей, состояние подключений к БД и Redis, результат вызовов интеграций.
3. Журналы не должны содержать пароли, токены, полные медицинские сведения и незамаскированные ПДн.
4. Действия, меняющие записи и расписания, должны фиксироваться в аудите с указанием субъекта, времени, типа действия и затронутого объекта.

## 3. Функциональные требования

### 3.1. Учётные записи и доступ

1. Система должна поддерживать вход пациента, врача и административных пользователей.
2. Для производственного контура должна быть предусмотрена интеграция с CityOS Identity по OIDC через Keycloak.
3. В системе должны применяться ролевые и объектные проверки доступа.
4. Сессия и токены должны обрабатываться безопасно; доступ должен отзываться при блокировке учётной записи или изменении её полномочий.
5. Пользователь должен видеть и менять только сведения, доступные его роли и контексту.

### 3.2. Каталог

1. Пациент должен иметь возможность просматривать список клиник и филиалов, врачей и специальностей.
2. Каталог должен поддерживать поиск и фильтрацию как минимум по специальности, врачу, клинике и филиалу.
3. Карточка врача должна содержать согласованный набор публичных сведений: имя, специальности, место приёма и доступные интервалы записи.
4. Администратор должен иметь возможность создавать и изменять справочные записи в пределах своих полномочий.
5. При наличии геоданных система должна поддерживать поиск клиник по расстоянию и передавать выбранный адрес сервису маршрутов.

### 3.3. Расписание и доступность

1. Система должна позволять уполномоченному пользователю задавать рабочие интервалы врача, длительность приёма и исключения из расписания.
2. Поддерживаемые длительности приёма: 15, 30 и 60 минут; конкретные значения задаются для услуги или расписания.
3. Система должна учитывать выходные, закрытые интервалы, отпуск врача, технические перерывы и буферы.
4. Доступность слота должна учитывать занятые записи, буфер, квоты и статус расписания.
5. Система должна предоставлять поиск доступных слотов по врачу, специальности, клинике, дате и типу оплаты.
6. Свободное время в выдаче является предварительной доступностью и подтверждается только при успешном создании записи.

### 3.4. Создание записи

1. Пациент должен иметь возможность выбрать врача или специальность, клинику, услугу, дату, доступное время и тип оплаты.
2. До подтверждения записи система должна показать выбранные параметры и запросить необходимые согласия.
3. При создании записи система должна атомарно проверить, что слот доступен, квота не исчерпана, а у врача и пациента нет конфликтующей записи.
4. Врач не может иметь пересекающиеся записи с учётом длительности и буфера.
5. Пациент не может иметь две пересекающиеся записи.
6. Успешное бронирование должно получить уникальный идентификатор и начальный статус, а пациенту должно быть показано подтверждение.
7. Повтор запроса с тем же ключом идемпотентности должен вернуть результат исходной операции.
8. Для записей должны поддерживаться квоты по типу оплаты: ОМС, ДМС и платная услуга.

### 3.5. Отмена и перенос

1. Пациент должен иметь возможность отменить собственную запись с учётом настроенных правил отмены.
2. Уполномоченный сотрудник должен иметь возможность отменить запись с указанием причины.
3. Пациент должен иметь возможность перенести запись на доступный слот.
4. Перенос должен выполняться атомарно: исходная запись сохраняется, если новый слот не удалось подтвердить.
5. После отмены или переноса должны обновляться занятость и квоты, а действие должно попадать в аудит.
6. Система должна уведомлять затронутого пациента и, при необходимости, врача.

### 3.6. Рабочее место врача и оператора

1. Врач должен видеть своё расписание за выбранный день и список относящихся к нему записей.
2. Представление расписания должно показывать время, статус записи и минимально необходимые сведения о пациенте.
3. Оператор должен иметь возможность искать и просматривать записи только в пределах своих полномочий.
4. Система должна поддерживать изменение статуса записи уполномоченным персоналом, включая отметку о состоявшемся приёме и неявке, если эти статусы включены в процесс клиники.

### 3.7. Лист ожидания

1. Если подходящих слотов нет, пациент должен иметь возможность оставить запрос на лист ожидания с указанием предпочтений.
2. Запрос должен содержать допустимые интервалы дат и времени, специалиста или врача, филиал и тип оплаты.
3. При освобождении подходящего слота система должна найти подходящие запросы и поставить уведомление в очередь на отправку.
4. Правила приоритета, срок удержания освобождённого слота и подтверждение пациентом должны настраиваться и быть одинаковы для всех каналов записи.
5. Пациент должен иметь возможность отказаться от листа ожидания.

### 3.8. Согласия и документы

1. До сбора и обработки ПДн система должна предоставить пациенту информацию о целях и условиях обработки и зафиксировать его согласие в требуемом объёме.
2. Для базового сценария должно поддерживаться подтверждение согласия в интерфейсе с фиксацией версии текста и времени.
3. При подключении ЭДО система должна передавать документ на подписание, получать статус и связывать результат с соответствующей записью или пациентом.
4. Отсутствие ответа ЭДО не должно приводить к потере других данных; доступность записи при неподписанном документе определяется правилами конкретной услуги.

### 3.9. Уведомления

1. Система должна ставить в очередь уведомления о создании, переносе и отмене записи, а также о приближении приёма.
2. Для производственного сценария должны поддерживаться уведомления за день и за час до приёма, если пациент выбрал соответствующий канал и это разрешено.
3. Каналы: push, SMS и электронная почта — в зависимости от подключённых поставщиков и настроек пациента.
4. Результат доставки и число попыток должны фиксироваться; повторная обработка не должна порождать дубликаты уведомлений.
5. Содержание уведомлений должно минимизировать раскрытие медицинской информации.

### 3.10. Внешние сервисы и расширенные сценарии

1. После записи система может запросить у CityOS Transport маршрут от выбранной точки пациента до филиала и отобразить результат.
2. При недоступности сервиса транспорта запись остаётся созданной, а пользователю сообщается, что маршрут временно недоступен.
3. При наличии разрешения пациента система может получить последние показатели из Vitals и показать их уполномоченному медицинскому работнику.
4. Доступ к данным Vitals должен отдельно проверяться и фиксироваться в аудите.
5. Система должна поддерживать запросы расписания с фильтрацией по географической близости при наличии координат клиник и разрешения на использование геолокации.

### 3.11. Мультиклиника и аналитика

1. Система должна поддерживать несколько филиалов с отдельными расписаниями, часовыми поясами, услугами и квотами.
2. Единый каталог должен позволять искать специалистов и доступные интервалы во всех доступных филиалах.
3. Уполномоченный руководитель должен иметь доступ к агрегированным показателям загрузки врачей, длительности приёма и доли неявок.
4. Аналитические отчёты не должны раскрывать персональные данные пациентов пользователям, которым они не нужны для работы.

### 3.12. Аудит

1. Система должна фиксировать создание, изменение, отмену и перенос записи, изменение расписания и квот, операции с согласиями и доступ к чувствительным сведениям.
2. Запись аудита должна содержать идентификатор субъекта, действие, объект, время, результат и источник запроса в допустимом объёме.
3. Обычные пользователи и прикладные роли не должны иметь возможности изменять или удалять уже записанные события аудита.

## 4. Нефункциональные требования

### 4.1. Безопасность

1. Все запросы к базе данных должны быть параметризованными; динамическая конкатенация пользовательского ввода в SQL запрещена.
2. Все входные данные должны проверяться по типу, длине, формату и допустимым значениям.
3. Запись, отмена и перенос должны быть защищены от гонок запросов с помощью транзакций и подходящих блокировок или ограничений целостности.
4. Изменяющие операции должны поддерживать идемпотентность.
5. Публичные API должны применять ограничение частоты запросов и защиту от автоматизированного массового бронирования.
6. Доступ должен предоставляться по принципу минимально необходимых полномочий; проверки должны учитывать и роль, и конкретный объект.
7. Передача данных должна использовать защищённые протоколы. Секреты должны храниться в механизме управления секретами целевой среды.
8. Система должна защищать веб-интерфейсы и API от распространённых атак, включая SQL-инъекции, XSS, CSRF, перебор учётных данных и IDOR.
9. Доступ к ПДн и медицинским сведениям должен журналироваться. ПДн должны маскироваться в логах и трассировках.
10. Должны быть предусмотрены правила хранения, архивирования и удаления данных в соответствии с утверждёнными требованиями организации и применимым законодательством.

### 4.2. Производительность и масштабирование

1. Типовые запросы каталога и доступности расписания должны выполняться с задержкой, пригодной для интерактивного интерфейса; целевое значение p95 должно быть определено для производственной нагрузки.
2. Система должна поддерживать горизонтальное масштабирование stateless-компонентов.
3. Нагрузка не должна приводить к созданию конфликтующих записей или потере подтверждённых операций.
4. Кэш расписания может использоваться для чтения, но подтверждение бронирования всегда должно проверять актуальное состояние в источнике истины.
5. Изменение записи или расписания должно инвалидировать либо обновлять связанные кэшированные данные.

### 4.3. Доступность и устойчивость

1. Сбой необязательной интеграции не должен блокировать основные операции регистратуры.
2. Повторные вызовы должны иметь ограничение по времени и числу попыток; фоновые задания должны восстанавливаться после перезапуска.
3. При недоступности Redis система должна либо безопасно деградировать, либо сообщить о временной недоступности функций, требующих очереди или кэша; подтверждённые записи не должны теряться.
4. Для PostgreSQL должны быть предусмотрены резервные копии и проверка их восстановления.
5. Целевые показатели доступности, RPO и RTO должны быть определены владельцем системы до промышленной эксплуатации.

### 4.4. Конкурентность и корректность

1. Для нескольких одновременных запросов на один слот может быть подтверждена не более чем одна запись.
2. После обработки конкурентных запросов данные о слотах, квотах, записях и листе ожидания должны оставаться согласованными.
3. Отказ операции должен приводить к полному откату её изменений либо к явно определённому безопасному промежуточному статусу.
4. Очереди и события должны обрабатываться с учётом возможной повторной доставки.

### 4.5. Удобство и доступность интерфейса

1. Интерфейсы должны адаптироваться к мобильным и настольным экранам.
2. Ошибки и недоступность слотов должны отображаться понятным языком с предложением допустимого следующего действия.
3. Ключевые сценарии должны быть доступны с клавиатуры и иметь подписи для элементов управления.
4. Интерфейс должен явно показывать филиал, дату, локальное время, длительность услуги и тип оплаты до подтверждения записи.

### 4.6. Сопровождаемость и совместимость

1. Код и API должны быть типизированы, а критичные доменные правила — отделены от транспортного слоя и UI.
2. Миграции базы данных должны быть воспроизводимыми и иметь порядок применения.
3. Изменения конфигурации и API должны документироваться.
4. Система должна поддерживать раздельные настройки сред без копирования секретов в репозиторий.
5. Клиентские приложения должны корректно обрабатывать ошибки API и неизвестные дополнительные поля ответа.

### 4.7. Соответствие требованиям и документация

1. Обработка ПДн должна проектироваться с учётом применимого законодательства Российской Федерации, включая требования к персональным данным.
2. Архитектура и процессы должны позволять подготовить документы по защите медицинских данных и применимым стандартам медицинской документации.
3. Должны быть предусмотрены эксплуатационная документация, описание архитектуры, инструкции по резервному копированию и восстановлению, а также порядок действий при отказе БД, Redis и внешних интеграций.
4. Конкретные юридические основания обработки, сроки хранения, состав обязательных документов и требования к сертификации должны быть подтверждены ответственными за правовое и информационно-безопасностное сопровождение до промышленного использования.

Изменения кодов и объединение филиалов должны выполняться контролируемой административной операцией с сохранением истории.

### А.3. Правила использования справочника

1. Каждая физическая точка обслуживания является отдельным филиалом и имеет собственный уникальный код. Две точки Nexon Express Care поэтому представлены отдельными строками.

6. Перед загрузкой справочника в промышленную среду владелец данных должен подтвердить адреса, классификацию филиалов и правила их публикации.
