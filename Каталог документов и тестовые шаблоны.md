# Каталог документов Nexon EDO и тестовые шаблоны

## Назначение и ограничения

Документ задаёт стартовый каталог типов для Nexon EDO и примеры содержимого для ручного прогона, демонстрации и автоматизированных тестов.

Все имена, идентификаторы, даты, учреждения и сведения о здоровье относятся к вымышленной вселенной CityOS. Готовые шаблоны документов для этой вселенной находятся в папке [Документы](Документы/README.md); примеры ниже остаются фикстурами для тестирования отдельных функций и граничных случаев.

## Общие правила шаблонов

- Каждый документ получает `documentId`, тип, автора, пациента, клинику, дату создания и номер версии.
- Подпись относится к конкретным байтам конкретной версии. Изменение содержания создаёт новую версию и требует новой подписи.
- Персональные и медицинские поля в примерах синтетические; тестовые данные нельзя подменять данными реальных пациентов.
- Для каждого типа задаются обязательные поля, роли подписантов, маршрут согласования и срок хранения.
- Хэш, подпись, сертификат, отметки времени и решения согласующих хранятся как атрибуты документа и события аудита, а не вставляются в свободный текст шаблона.
- Для тестирования следует отдельно проверять пустые обязательные поля, недопустимые переходы статусов, повторные команды, отказ подписи, смену версии и проверку подписи после архивирования.

## Перечень документов

| Код | Документ | Кто создаёт | Типовой маршрут | Результат |
|---|---|---|---|---|
| `CLINICAL_CONCLUSION` | Заключение врача | Врач | Автор → подпись врача | Подписанное заключение |
| `REFERRAL` | Направление | Врач | Автор → подпись врача; при настройке — согласование | Подписанное направление для Registry/принимающей клиники |
| `PRESCRIPTION` | Рецепт | Врач | Автор → главный врач/уполномоченный согласующий → подпись | Подписанный рецепт либо возврат на исправление |
| `INTERVENTION_CONSENT` | Согласие пациента на вмешательство | Медработник формирует; пациент подтверждает | Подготовка → ознакомление пациента → подтверждение/подпись пациента и требуемая подпись медработника | Зафиксированное согласие либо отказ |
| `EXAMINATION_ACT` | Акт обследования | Врач или комиссия | Автор(ы) → требуемые подписи участников | Подписанный акт |
| `PERSONAL_DATA_CONSENT` | Согласие на обработку ПДн (если входит в объём ЭДО) | Система или уполномоченный сотрудник | Предъявление текста → действие пациента → фиксация версии и подтверждения | Запись о принятом согласии или отказе |

Последний тип может оставаться в Registry, если по архитектуре и утверждённому процессу он не требует хранения в ЭДО. Это решение должно быть единым для обеих систем.

## Набор сквозных прогонов

1. **Успешное подписание:** создать `CLINICAL_CONCLUSION`, сохранить черновик, подписать версию 1, проверить подпись и увидеть аудит.
2. **Новая версия:** изменить подписанный документ, получить версию 2; подпись версии 1 остаётся проверяемой, версия 2 требует отдельной подписи.
3. **Согласование рецепта:** отправить `PRESCRIPTION` на проверку, вернуть на исправление, сохранить новую версию, согласовать и подписать.
4. **Подпись недоступна:** имитировать ошибку PKCS#11; документ не становится `signed`, событие аудита создаётся, повтор безопасен.
5. **Отказ пациента:** зафиксировать `declined`; Registry получает отказ, но система не отображает его как действующее согласие.
6. **Межсервисный повтор:** повторить запрос Registry с тем же ключом идемпотентности; EDO возвращает существующий `documentId`.
7. **Проверка доступа:** открыть документ из-под пользователя без прав; содержимое не выдаётся, отказ журналируется.
8. **Unicode и форматирование:** проверить кириллицу, `Ё`, переносы строк и спецсимволы в отображении, PDF и подписываемом содержимом.

## Минимальные метаданные для API и аудита

```json
{
  "documentId": "edo-test-0001",
  "documentType": "CLINICAL_CONCLUSION",
  "version": 1,
  "patientId": "patient-test-001",
  "appointmentId": "appointment-test-001",
  "clinicId": "NX-CENT-001",
  "authorId": "doctor-test-001",
  "status": "signed",
  "contentHash": "sha256:<test-value>",
  "signatureId": "signature-test-001",
  "certificateId": "certificate-test-001",
  "createdAt": "2030-04-12T09:30:00Z",
  "signedAt": "2030-04-12T09:32:00Z"
}
```

`<test-value>` — заглушка, а не действительный хэш. Интеграционный ответ не должен раскрывать приватный ключ, PIN токена или секреты HSM.
