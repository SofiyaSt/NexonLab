# Пояснение: контракт внешней интеграции

## Что называется контрактом

Контракт интеграции — это согласованное описание того, как Nexon Registry и внешний сервис обмениваются запросами и результатами. Он позволяет понять, какие данные отправлять, какой ответ ожидать и как действовать при ошибке.

Контракт фиксируется отдельно для каждой интеграции и операции. Он должен включать:

- назначение операции и систему — владельца вызываемого API;
- версию API внешней системы и способ её указания (например, `/v1/` в пути, заголовок или версия схемы сообщений);
- адрес и HTTP-метод либо тип сообщения;
- поля запроса и ответа, их типы, обязательность, форматы и допустимые значения;
- способ аутентификации и необходимые разрешения;
- возможные ошибки и их интерпретацию;
- тайм-ауты, повторы, идемпотентность и поведение при недоступности;
- ограничения по передаваемым персональным и медицинским данным.

## Версия API внешней системы и версия API Registry

Это разные версии. В контракте интеграции фиксируется версия API поставщика, с которым работает адаптер Registry. Если поставщик изменит API, адаптер можно обновить или переключить на новую версию, сохраняя внутренний интерфейс Registry для остальных компонентов.

Версия API Nexon Registry для мобильного приложения или кабинета врача описывает отдельный контракт между Registry и этими клиентами. Требования к ней изложены в основном ТЗ в разделе 2.1.

## Роль адаптера

Адаптер — компонент на границе Registry, который преобразует внутренние запросы и модели в формат конкретного внешнего API и переводит ответы и ошибки обратно во внутренний формат. Доменная логика записи не должна зависеть от особенностей URL, полей или кодов ошибок одного поставщика.

Например, внутренний запрос `получить маршрут до филиала` адаптер преобразует в запрос конкретной версии CityOS Transport API. Если версия API изменится, основное приложение продолжает обращаться к тому же внутреннему интерфейсу, а изменения локализуются в адаптере и его контракте.

## Управление изменениями

При обновлении внешнего контракта необходимо проверить совместимость форматов, авторизацию, ошибки и поведение повторов. Несовместимую версию нельзя вводить без согласованного переключения адаптера и проверки зависимых сценариев. Для каждой интеграции следует указывать ответственного владельца контракта и актуальную версию в технической документации.
