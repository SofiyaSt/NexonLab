# Задание 1 (переработанное): «Nexon Registry» — Единая электронная регистратура

## Концепция

Вместо legacy-рефакторинга делаем **построение с нуля** — но с фокусом на сложную бизнес-логику и security-by-design. Это точка входа для пациентов и врачей Иннополиса: запись на приём, расписание, согласия, маршруты до клиники.

**Ключевая идея:** система не существует в вакууме — она **агрегирует данные из других сервисов Nexon Labs** и выступает BFF (Backend-for-Frontend) для мобильного приложения пациента и кабинета врача в поликлинике.

**Лор:**
> В каждой клинике Иннополиса раньше была своя бумажная регистратура. CityOS требует единый цифровой фронт-офис: пациент записывается через приложение, врач видит расписание в едином кабинете, а все согласия и направления подписываются через ЭДО.

---

## Стек

- **Backend:** Node.js 22 + TypeScript + MoleculerJS
- **Frontend:** React + Vite + TypeScript (2 приложения: пациент / врач)
- **БД:** PostgreSQL + Redis (кэш + очереди)
- **Очереди:** BullMQ
- **Транспорт:** REST + GraphQL (для гибких запросов расписания)

## Layer 1: MVP (14 дней)

**Цель:** Работающая запись на приём, локально через Compose.

### Функционал
- Каталог врачей и специальностей
- Расписание приёмов (слоты по 15/30/60 минут)
- Запись пациента на приём (с выбором врача, даты, времени)
- Отмена и перенос записи
- Базовый UI: пациент записывается, врач видит свой список на день
- Согласие на обработку ПДн (простая галочка, без подписи)

### Сложная бизнес-логика (это и есть "мясо" задания)
- **Пересечения слотов:** врач не может быть записан в два места одновременно
- **Двойная запись:** один пациент не может быть у двух врачей в одно время
- **Буфер между приёмами:** после сложного приёма нужен перерыв
- **Квоты по полисам:** ОМС / ДМС / платные — разные квоты на врача
- **Лист ожидания:** если слотов нет, пациент встаёт в очередь и получает уведомление при освобождении

### Security-by-design (вместо фикса багов)
Студенты с самого начала проектируют систему так, чтобы **багов из старой версии не возникло**:
- Только параметризованные запросы (никакой конкатенации SQL)
- Все операции записи — в транзакциях с `SELECT ... FOR UPDATE`
- Идемпотентность по `Idempotency-Key`
- Rate limiting на API записи (защита от ботов, скупающих слоты)
- Валидация входных данных через class-validator

### Что сдаётся
- [ ] Пациент записывается, отменяет, переносит запись
- [ ] Врач видит своё расписание на день
- [ ] Нет пересечений: 50 параллельных записей на один слот → ровно 1 успех
- [ ] `docker-compose up` поднимает всё одной командой
- [ ] Unit-тесты на бизнес-логику (Vitest)
- [ ] README: как запустить локально

### Роль ментора
- Консультирует по транзакциям и блокировкам
- Проверяет, что race condition не возникает

## Layer 2: Production (14 дней)

**Цель:** Деплой в Swarm, SSO, интеграции, наблюдаемость.

### Функционал (дополнительно)
- **SSO через CityOS Identity** (OIDC, Keycloak): пациент и врач входят через единый аккаунт
- **Два фронта:** мобильное приложение пациента + кабинет врача
- **GraphQL API** для гибких запросов расписания ("покажи все свободные слоты у кардиологов в радиусе 2 км от меня")
- **Уведомления:** SMS / push / email за день до приёма, за час, при отмене врачом
- **Интеграция с метро-полигоном:** после записи система строит маршрут от дома пациента до клиники через CityOS Transport API (ваш симулятор)
- **Интеграция с ЭДО (Группа 4):** перед приёмом пациент подписывает согласие на вмешательство через ЭДО
- **Интеграция с Vitals (Группа 3):** в карточке врача видны последние показатели браслета пациента

### DevOps / Инфраструктура
- Деплой в Swarm через `docker stack deploy`
- Секреты в Vault (пароли БД, API-ключи)
- CI/CD: GitLab pipeline (lint → typecheck → test → build → deploy)
- Мониторинг: Prometheus + Grafana (метрики API, БД, очередей)
- Логи: Loki (централизованные)
- APM: OpenTelemetry (трейсинг запросов от фронта до БД)
- Кэширование расписания в Redis (invalidation при изменении)

### Security
- mTLS между сервисами
- Rate limiting на публичных эндпоинтах
- Аудит-лог: кто, когда, к кому записался / отменил
- Защита от "скупки слотов" (боты, которые записывают всех на одного врача)

### Что сдаётся
- [ ] SSO работает: вход через Keycloak
- [ ] Деплой в Swarm, секреты не в коде
- [ ] CI зелёный, деплой автоматический
- [ ] Интеграция с метро-полигоном: маршрут строится после записи
- [ ] Интеграция с ЭДО: согласие подписывается
- [ ] Дашборд в Grafana: latency p95, error rate, RPS
- [ ] Нагрузочный тест: 100 rps × 30 сек, 0 ошибок
- [ ] Уведомления доходят до пациента

### Роль ментора
- Помогает с OIDC-интеграцией
- Настраивает шаблоны Prometheus/Loki
- Координирует контракты с Г4 (ЭДО) и Г3 (Vitals)
- Принимает деплой в Swarm

## Layer 3: Enterprise (14 дней)

**Цель:** Отказоустойчивость, масштабирование, compliance, DR.

### Функционал (дополнительно)
- **BFF-паттерн:** отдельные API для мобильного приложения и веб-кабинета врача (разная оптимизация)
- **Умное расписание:** система предлагает пациенту "лучшее время" с учётом его геолокации, загрузки врача и транспортной доступности
- **Аналитика для главврача:** загрузка врачей, среднее время приёма, no-show rate
- **Мультиклиника:** поддержка нескольких филиалов Nexon Labs с единым расписанием

### Инфраструктура / Отказоустойчивость
- **PostgreSQL replica set:** primary + 2 standby, автоматический failover
- **Redis Sentinel** для кэша
- **Бэкапы БД** с проверкой восстановления (еженедельный DR-тест)
- **Circuit breaker** для внешних вызовов (метро-полигон, ЭДО, Vitals) — если внешний сервис упал, запись всё равно работает
- **Graceful shutdown** при деплое: активные записи не теряются
- **Нагрузочный тест:** 500 rps × 60 сек, 0 ошибок

### Security / Compliance
- **Penetration test:** ментор пытается сломать систему (SQLi, XSS, CSRF, IDOR)
- **Compliance:** документация по 152-ФЗ (ПДн пациентов), ГОСТ Р 58761-2019 (ЭМК)
- **Аудит-лог в append-only хранилище** (невозможно подделать)
- **Data retention:** архивация старых записей по истечении срока хранения
- **DLP-контроль:** маскирование ПДн в логах

### Документация
- `runbook.md`: что делать, если БД упала / Redis недоступен / метро-полигон не отвечает
- Архитектурная схема (C4 model)
- SLA-документ: 99.9% uptime, RTO < 5 мин, RPO < 1 час

### Что сдаётся
- [ ] **DR-тест:** primary PostgreSQL упал → standby стал primary, данные не потеряны
- [ ] **Бэкап восстановлен:** данные за последние 24 часа на месте
- [ ] **Pen test:** 0 критических уязвимостей (отчёт)
- [ ] **Circuit breaker:** метро-полигон упал → запись работает, маршрут не строится (деградация, а не падение)
- [ ] **Нагрузочный тест:** 500 rps, latency p95 < 500ms
- [ ] **Compliance-документация** по 152-ФЗ
- [ ] `runbook.md` + архитектурная схема
- [ ] Аудит-лог: видно каждое действие с записью

### Роль ментора
- **Проводит pen test** (пытается сломать систему)
- **Проверяет DR-сценарий** (удаляет primary, смотрит на failover)
- Консультирует по compliance
- Принимает документацию

## Связь с другими группами

```
                    ┌─────────────────────────┐
                    │   Nexon Registry (Г1)   │
                    │   BFF для пациента/врача│
                    └───────────┬─────────────┘
                                │
        ┌───────────────┬───────┼───────┐
        ▼               ▼       ▼       ▼
  CityOS Identity  ЭДО (Г4)  Vitals  Meet (Г2)
  (SSO, OIDC)    (согласия)  (Г3)  (консилиумы)
```

**Г1 — это "клей"**, который связывает все сервисы в единый пользовательский опыт. Без неё пациенту пришлось бы ходить в 5 разных приложений.

## Почему это лучше legacy-задания

| Критерий | Legacy (старый вариант) | Registry (новый вариант) |
|---|---|---|
| Ценность для студентов | Фикс чужих багов | Построение системы с нуля + security-by-design |
| Связь с другими группами | Слабая (только SSO) | Сильная (BFF для всех сервисов) |
| Сложность Layer 3 | Pen test + DR | Pen test + DR + circuit breaker + compliance |
| Реалистичность | Legacy бывает редко | BFF-паттерн — стандарт в энтерпрайзе |
