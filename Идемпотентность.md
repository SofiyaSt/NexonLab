# Пояснение: ключ идемпотентности

## Для чего нужен ключ

Ключ идемпотентности защищает от повторного выполнения одной и той же операции, если клиент не получил ответ сервера и повторил запрос. Он особенно важен для мобильных приложений, где соединение может прерваться в любой момент.

### Пример с созданием записи

1. Мобильное приложение отправляет запрос `POST /api/v1/appointments`.
2. Сервер сохраняет запись в базе данных.
3. Ответ `201 Created` теряется из-за обрыва соединения.
4. Приложение не знает, создалась ли запись, и повторяет запрос.
5. Сервер распознаёт повтор по `Idempotency-Key` и возвращает результат первой операции, не создавая вторую запись.

Без ключа повторный запрос мог бы создать дубликат. Проверка доступности слота сама по себе не решает эту проблему во всех случаях: например, повтор мог бы занять другой свободный слот, если параметры запроса успели измениться.

## Как использует ключ клиент

- Для каждой новой логической операции клиент создаёт новый уникальный ключ.
- При сетевом тайм-ауте или неопределённом результате клиент повторяет запрос с тем же ключом и теми же параметрами.
- Для новой операции, даже если она похожа на предыдущую, клиент создаёт новый ключ.
- Клиент не должен считать операцию неуспешной только потому, что не получил ответ. Он может повторить запрос с исходным ключом или запросить состояние созданной записи.

Пример:

```http
POST /api/v1/appointments
Idempotency-Key: 7e8c7d3a-62b2-4d3d-9a4a-9c90f33e2d11
Content-Type: application/json

{
  "doctorId": "doctor-123",
  "slotId": "slot-456",
  "paymentType": "insurance"
}
```

Значение заголовка здесь иллюстративное. Формат и способ генерации ключа должны быть единообразно определены API-контрактом.

## Как обрабатывает ключ сервер

Сервер должен:

1. Определять ключ в контексте пользователя или клиента и конкретной операции/эндпоинта, чтобы ключи разных пользователей или разных операций не пересекались.
2. Сохранять сведения о ключе и результате операции согласованно с изменением записи в БД. Для бронирования запись и результат идемпотентности должны фиксироваться атомарно.
3. При повторе того же запроса возвращать сохранённый результат исходной операции, например тот же идентификатор записи и соответствующий HTTP-статус.
4. Если тот же ключ повторно использован с другими значимыми параметрами, отклонять запрос как конфликт, а не выполнять новую операцию и не возвращать результат для других параметров.
5. Корректно обрабатывать два одновременных запроса с одним ключом: операция должна произойти один раз, а повтор должен получить исходный результат либо понятный временный ответ о том, что операция ещё обрабатывается.
6. Хранить ключи ограниченное время. Срок хранения и поведение после его истечения должны быть определены контрактом API с учётом максимального периода автоматических повторов клиента.

Ключ идемпотентности не заменяет аутентификацию и проверку прав, транзакции, проверку доступности слота, ограничение частоты запросов или защиту от разных операций, одновременно претендующих на один слот.

## Область применения в Nexon Registry

Ключ применяется к изменяющим операциям, где безопасный повтор важен: создание, перенос и отмена записи. Его также следует учитывать при повторной отправке команд внешним сервисам, если повтор может создать документ, платёж или уведомление.

Правила идемпотентности не означают, что система Nexon Registry обязательно принимает или списывает оплату. Если платёжный процесс будет включён в объём системы, для него требуется отдельный контракт с платёжным провайдером и собственные правила идемпотентности.
