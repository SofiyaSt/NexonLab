# Переход на PHP для ЭДО с SoftHSM2

## Назначение

Документ описывает архитектурные последствия замены backend на TypeScript + MoleculerJS на PHP при интеграции с ЭДО и PKCS#11-модулем SoftHSM2. Это архитектурная оценка, а не замер производительности: окончательный выбор рантайма и способа работы с токеном следует подтвердить прототипом под ожидаемой нагрузкой.

## Краткий вывод

Переход на PHP возможен. Он не требует автоматически переносить каждый Moleculer-сервис в отдельный PHP-микросервис или внедрять Consul/Kafka. Для небольшого и среднего объёма разумная отправная точка — модульный PHP backend, HTTP API, PostgreSQL, очередь фоновых задач и отдельный изолированный компонент подписи, если PKCS#11-библиотека или требования безопасности этого требуют.

Основные изменения относятся к исполнению фоновых задач, обслуживанию процессов, интеграции криптографии и замене встроенных возможностей Moleculer инфраструктурными решениями. React сохраняет HTTP-контракт только при совместимости API; при переходе на асинхронную подпись клиентскому сценарию дополнительно понадобится получать статус задачи.

## Что меняется при переходе

### Работа с SoftHSM2 и PKCS#11

SoftHSM2 предоставляет криптографический модуль с интерфейсом PKCS#11. Приложение или отдельный подписывающий компонент загружает библиотеку, выбирает токен, открывает сессию и выполняет операции с ключами. Частный ключ должен оставаться в токене; PIN и доступ к каталогу токенов относятся к секретам и должны быть ограничены по доступу.

Нельзя считать, что PHP-FPM обязательно заново инициализирует PKCS#11 на каждый HTTP-запрос: FPM обслуживает запросы пулом процессов, а процесс может обработать несколько запросов. При этом жизненный цикл расширения, библиотеки и сессий зависит от конкретного PHP binding, конфигурации FPM и самой PKCS#11-библиотеки. Повторное использование состояния между запросами нельзя предполагать без проверки реализации и тестов.

Варианты размещения подписи:

1. **Подпись внутри PHP-приложения.** Подходит, если есть зрелый PKCS#11 binding для целевой версии PHP, его поведение при параллельной нагрузке проверено, а операционная команда умеет сопровождать его в целевой среде.
2. **Долгоживущий worker-процесс.** Подходит для фоновой подписи с очереди, если библиотека корректно поддерживает такой режим. Нужно проверить безопасную инициализацию, повторное подключение после ошибок и правила использования сессий при конкурентной работе.
3. **Отдельный signing service.** Изолирует PKCS#11-зависимость, PIN и права на токен от публичного API. Вызывать его следует по аутентифицированному внутреннему каналу с ограниченным набором операций. Такой сервис добавляет сетевой hop и становится критичной зависимостью, поэтому ему нужны тайм-ауты, метрики, аудит и план восстановления.

Выбор между этими вариантами определяется binding, требованиями изоляции ключей, ожидаемой нагрузкой и эксплуатационными ограничениями. SoftHSM2 удобен для разработки и тестирования PKCS#11-интеграции, но сам по себе не является аппаратным HSM и не подтверждает производительность или гарантии промышленного устройства.

### Процессы PHP и тяжёлые операции

PHP-FPM — процессный FastCGI менеджер с пулами рабочих процессов; это не означает отдельный новый PHP-процесс на каждый запрос. FPM можно использовать для обычного API и коротких операций. Длительную генерацию документов, проверку сертификатов и подписание обычно проще вынести в фоновые worker-процессы через очередь, чтобы HTTP-запрос быстро возвращал идентификатор операции.

Долгоживущий рантайм (например, RoadRunner или Swoole) может быть полезен, если важны постоянные соединения или общая память процесса. Он не обязателен только ради SoftHSM2 и требует дисциплины: состояние запроса, пользовательский контекст и ресурсы должны сбрасываться между задачами, а расширения должны корректно работать в таком рантайме.

Node.js тоже не делает CPU-тяжёлую работу автоматически неблокирующей: тяжёлые синхронные операции могут задерживать event loop. Очереди и отдельные worker-процессы полезны в обоих стеках.

### Вызовы между компонентами и обнаружение сервисов

Moleculer предоставляет service registry/discovery, балансировку, транспорт, вызовы действий, устойчивость, метрики и трассировку. При переносе PHP-кода эти возможности надо сопоставить с уже имеющейся инфраструктурой, а не механически заменять каждую Consul, gRPC или Kafka.

Возможные варианты связи:

- модульный монолит и локальные вызовы — для доменных модулей без необходимости независимого развёртывания;
- HTTP/REST — для синхронных запросов между небольшим числом сервисов;
- очередь и сообщения — для подписания, уведомлений и других фоновых операций;
- DNS или оркестратор — для обнаружения сервисов, если сервисы уже развёрнуты в соответствующей среде.

Laravel и Symfony могут работать с контейнерами, очередями и HTTP-клиентами, но не воспроизводят Moleculer автоматически. Hyperf и другие асинхронные PHP-решения — возможные варианты, однако выбирать их стоит под требования рантайма и компетенции команды. Service mesh нужен только при соответствующих сетевых и эксплуатационных требованиях.

### Очереди и клиентский сценарий

Если подписание или подготовка документа не укладывается в целевое время HTTP-запроса, API может принять команду и вернуть `202 Accepted` с `operationId`. Состояние задачи должно храниться в источнике истины, а постановка задачи и запись операции должны быть согласованы — например, через transactional outbox, чтобы не создать запись без сообщения в очереди или наоборот.

Клиент может получать статус через polling, SSE или WebSocket. WebSocket не обязателен: для нечастых обновлений polling или SSE проще в эксплуатации. Повторная доставка задачи не должна создавать повторную подпись или дублировать документ; для операции задаются устойчивый идентификатор, идемпотентность и конечные состояния, например `queued`, `processing`, `succeeded`, `failed`.

### Метрики и распределённая трассировка

Moleculer имеет собственную трассировку действий и событий, распространение span-контекста между узлами и экспортёры, включая Jaeger и Zipkin. Это не следует описывать как «OpenTelemetry одной строкой»: документация Moleculer отдельно указывает, что в core нет OTLP-экспортёра.

В PHP доступны OpenTelemetry API и варианты автоинструментации для ряда фреймворков и клиентов. При поддерживаемых библиотеках контекст трассировки может передаваться автоматически; ручной проброс нужен для неинструментированных границ и фоновых сообщений. Для очереди trace context следует включать в metadata сообщения. В любом стеке нужно явно инструментировать доменные операции, включая ожидание подписи и вызов PKCS#11.

Трассировки и логи не должны содержать PIN, закрытые ключи, содержимое подписываемых документов и избыточные персональные данные. Метрики должны включать длительность операций подписи, ошибки PKCS#11, длину очереди, повторные попытки и доступность токена.

## Рекомендуемая целевая схема

```text
React
  │ HTTPS / API
  ▼
PHP API (Laravel или Symfony, PHP-FPM)
  ├── PostgreSQL: заявки, документы, статусы, аудит, ключи идемпотентности
  ├── Outbox / очередь
  └── PHP worker ── внутренний API или локальная PKCS#11-библиотека ── SoftHSM2
          │
          └── обновляет статус операции и ставит уведомление

React получает статус через polling, SSE или WebSocket
```

На первом этапе PHP worker и API могут быть частью одного приложения, развёрнутыми разными процессами. Вынос подписи в самостоятельный сервис оправдан, если изоляция PKCS#11, независимое масштабирование или особый жизненный цикл библиотеки дают измеримую пользу.

## Что проверить прототипом до фиксации архитектуры

- Наличие и зрелость PKCS#11 binding для выбранной версии PHP и ОС; способ загрузки библиотеки и поддерживаемые операции.
- Инициализацию и завершение PKCS#11, открытие/закрытие сессий, конкурентность, повторное подключение после отказа и восстановление worker-процесса.
- Производительность подписания с реальным размером документов и параллелизмом; отдельно измерить задержку и частоту ошибок, а не экстраполировать по характеристикам SoftHSM2.
- Поведение при недоступном токене, неверном PIN, исчерпании сессий, рестарте процесса и повторной доставке сообщения.
- Хранение PIN и токен-базы, файловые права и границу доверия между API, очередью и компонентом подписи.
- Контракт API для асинхронного результата, идемпотентность и согласованность БД с очередью.
- Передачу trace context через HTTP и очередь, а также отсутствие секретов и содержимого документов в telemetry.

## Решения, которые нужно зафиксировать

До промышленного переноса следует выбрать:

- PHP runtime и фреймворк;
- будет ли подпись выполняться в PHP worker или отдельном signing service;
- очередь и гарантии доставки, стратегию outbox и дедупликации;
- канал статуса для React и его контракт;
- целевую нагрузку на подпись и измеримые критерии задержки/ошибок;
- эксплуатационные требования к секретам, резервированию, аудиту и восстановлению.

Пока эти параметры не заданы, рекомендация — начать с PHP API + фонового worker и вынести PKCS#11 за отдельную границу только после прототипа и проверки требований безопасности.
